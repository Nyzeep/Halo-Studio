# 可验证双 Agent 编码交付工作流

**状态：** 已确认，等待拆分实施任务

**日期：** 2026-07-24

**适用范围：** R1 核心边界完成后的首个用户可用纵向切片

## Problem Statement

Halo Studio 的 `develop` 工作树已经具备受信任工作区、Pi/OpenCode 受管运行时、受限 IPC、凭据隔离、SQLite 和基础会话适配能力，但本地开发者尚不能把一次编码委托从任务说明推进到可审阅、可解释、可恢复的交付结论。开发者无法清楚地区分自己原有的脏工作树修改与 Agent 新产生的修改，也无法在不依赖聊天记录或自动 Git 操作的情况下判断测试是否执行、交付是否可接受、失败后如何继续，或何时应把同一任务交给另一个 Agent。

BitFun 的运行时分层、窄接口和真实状态优先的做法可以作为架构参考，但其多 Agent、办公、远程、多端、MCP/插件生态和自动化编排不是 Halo Studio 的产品目标。Halo Studio 需要以更窄的本地开发者场景形成差异化：一个受信任 Git 工作区内，由用户显式选择 Pi 或 OpenCode，以可验证的 Git 增量和交付证据完成一次编码任务。

## Solution

在受信任的 Git 工作区中，本地开发者创建一个 **Agent 任务**：填写必需的 **任务说明**，显式选择 Pi 或 OpenCode 作为 **主 Agent**，并可选择性附带文件、已有 Diff 或补充说明。Halo 在开始前记录 **任务基线**，从而允许已有脏工作树存在，同时只将基线之后的变化归因于该任务。

任务由所选受管应用以其原生语义运行。Halo 显示短暂的 **运行时轨迹**、原生可用的操作请求和状态，但不伪造聊天能力、不代理 Agent 文件写入、不执行任意 Shell 或测试命令，也不自动重试、故障转移或委派。Agent 结束、取消或失败后，Halo 生成追加式的 **交付证据版本**，其中包含受限摘要、变更/Diff 证据和明确的 **验证结果**。开发者只对最新的 **可审阅交付** 作出接受或拒绝结论；两种结论都不产生 Git 写入。

若需要另一个 Agent 继续或审阅，开发者只能在当前 Agent 已结算并已产生证据后，预览一个有界的 **交接包** 并手动发起 **Agent 交接**。交接保留同一任务身份，接收方成为下一证据版本的主 Agent。所有任务、交付证据、交接包和结论仅保留在本地 **交付历史** 中，并受可见、用户控制的存储配额和清理流程保护；达到配额时不静默删除历史。

## User Stories

1. 作为本地开发者，我希望可以打开非 Git 文件夹查看基本项目信息，以便先检查目录而不被强制创建任务。
2. 作为本地开发者，我希望非 Git 工作区明确不能创建 Agent 任务，以免把无权威变更基线的目录误当成可验证项目。
3. 作为本地开发者，我希望未受信任工作区只能显示基本项目和 Git 信息，以便在确认信任前不启动运行时、不创建任务、不读取项目配置或交接内容。
4. 作为本地开发者，我希望只能在受信任 Git 工作区中创建 Agent 任务，以便任务权限与既有工作区信任边界一致。
5. 作为本地开发者，我希望创建任务时必须填写任务说明，以便每次编码委托都有清晰、可复查的目标。
6. 作为本地开发者，我希望明确选择 Pi 或 OpenCode 作为主 Agent，以便不会被系统自动分配、竞速或故障转移到另一个 Agent。
7. 作为本地开发者，我希望按需选择少量文件、已有 Diff 或补充说明加入任务，以便提供必要上下文而不自动泄露整个工作区或历史。
8. 作为本地开发者，我希望在提交前预览任务说明及其已选上下文，以便确认交给 Agent 的内容范围。
9. 作为本地开发者，我希望脏工作树仍能创建任务，以便不必 stash、提交、切换分支或先清理自己的在途修改。
10. 作为本地开发者，我希望创建任务时记录任务基线，以便审阅时只将其后的变化归因于当前任务。
11. 作为本地开发者，我希望任务基线能处理没有提交、已有暂存修改、未暂存修改和未跟踪文件，以便 Git 状态不完整时仍不会伪称变更来源。
12. 作为本地开发者，我希望任何无法可靠比较的预存修改都被明确标为受限或不可用，以便不会把不确定的 Diff 当成精确归因。
13. 作为本地开发者，我希望在任务开始前看到所选主 Agent 的真实可用性，以便不可用的 Pi 或 OpenCode 不会显示为可启动的假状态。
14. 作为本地开发者，我希望只在自己发起时开始、取消或再次运行任务，以便 Halo 不自动重试、自动委派或自动改选 Agent。
15. 作为本地开发者，我希望 Agent 继续以原生权限模型直接修改受信任工作区，以便 Halo 不成为额外的文件写入代理或虚假的沙箱。
16. 作为本地开发者，我希望在运行期间看到有限的运行时轨迹、工具状态和原生操作请求，以便理解当前任务正在等待什么。
17. 作为本地开发者，我希望只有 Agent 真正支持的权限或澄清通道才显示为可操作请求，以便 Halo 不凭空制造通用批准对话框。
18. 作为本地开发者，我希望运行时轨迹默认不成为完整对话或原始日志档案，以便降低敏感内容和长期存储责任。
19. 作为本地开发者，我希望可以看到任务是否在运行、等待原生操作、已结算、已取消或失败，以便准确判断下一步。
20. 作为本地开发者，我希望取消任务会请求所选 Agent 原生停止，同时保留已经产生的部分修改与证据，以便可以自行检查或继续处理。
21. 作为本地开发者，我希望运行时失败会保留可恢复的失败原因，以便我能手动决定修复环境、再次运行或交接，而不是被系统暗中重试。
22. 作为本地开发者，我希望每次运行、手动再次运行或交接后的继续工作都形成新的交付证据版本，以便旧结论不会被覆盖。
23. 作为本地开发者，我希望可审阅交付包含主 Agent 摘要、变更证据和验证结果，以便不必从完整聊天记录推断结果。
24. 作为本地开发者，我希望交付证据能区分新增、修改、删除、不可比较、已截断和当前工作区不可用的状态，以便准确理解证据完整性。
25. 作为本地开发者，我希望持久化的 Diff 证据经过脱敏和大小限制，以便本地历史不意外成为凭据或超大文件的副本。
26. 作为本地开发者，我希望需要时从当前 Git 工作区按需读取完整原始 Diff，以便在工作区仍可比较时检查真实细节。
27. 作为本地开发者，我希望完整原始 Diff 无法读取、基线不足或当前工作区已变化时收到明确原因，以便不把缺失数据误认为没有改动。
28. 作为本地开发者，我希望验证结果明确显示原生 Agent 报告的通过、失败或未执行，以便 Halo 不暗中运行测试或把未执行伪装为通过。
29. 作为本地开发者，我希望只能接受或拒绝最新的可审阅交付，以便不会对过期证据作出当前任务结论。
30. 作为本地开发者，我希望接受交付只记录结论，不自动提交、建分支、切换工作树、创建 PR、部署或修改 Git 状态，以便版本控制仍由我掌控。
31. 作为本地开发者，我希望拒绝交付仍保留文件、任务和证据历史，以便不丢失可供后续修正的材料，也不触发自动回滚。
32. 作为本地开发者，我希望可以在当前 Agent 已结算后发起交接，以便把同一任务交给另一受管应用继续或审阅。
33. 作为本地开发者，我希望在交接前预览并确认一个有界交接包，以便决定是否共享任务目标、摘要、选定变更和验证结果。
34. 作为本地开发者，我希望交接包默认排除完整对话、原始日志、凭据和配置文件，以便避免把不必要的敏感上下文传给另一个 Agent。
35. 作为本地开发者，我希望交接不创建新任务身份，接收 Agent 成为下一证据版本的主 Agent，以便整个交付链可以连续审阅。
36. 作为本地开发者，我希望“审阅请求”只表达目的而不承诺强制只读，以便任何实际修改都能被诚实地纳入新的交付证据版本。
37. 作为本地开发者，我希望在另一个 Agent 不可用时仍能查看其他可用 Agent 与已有证据，以便单一运行时故障不会伪装成整个工作台离线。
38. 作为本地开发者，我希望交付历史仅保存在本机，不自动同步到云端，以便本地代码与工作记录不离开我的设备。
39. 作为本地开发者，我希望查看历史使用量、调整配额并预览清理目标，以便由自己控制保留哪些任务和证据。
40. 作为本地开发者，我希望配额不足时被要求显式清理或增加配额，以便 Halo 不静默删除旧任务、证据或交接包。
41. 作为本地开发者，我希望清理操作显示将删除的历史范围与可恢复性，以便能够有意识地管理本地存储。
42. 作为维护者，我希望任务、证据、交接和配额通过固定、受 Schema 校验的 IPC 暴露，以便 Renderer 永远不能获得任意文件、Git、Shell、凭据或数据库访问。
43. 作为维护者，我希望项目只借鉴 BitFun 的模块边界和真实状态原则而不复制其代码、资源或平台范围，以便 Halo 保持独立定位并遵守许可证边界。

## Implementation Decisions

- 本阶段的产品边界是“面向个人本地开发者的可验证双 Agent 编码交付”，不是聊天优先的通用 AI 应用、Agent 市场、远程任务平台或完整 IDE。受管应用仍只有 Pi 和 OpenCode。
- 新功能以 **Agent 任务**、**任务基线**、**交付证据**、**交付证据版本**、**可审阅交付**、**交接包**、**Agent 交接** 和 **交付历史** 为稳定领域语言；这些词的定义以根 `CONTEXT.md` 为准。
- 创建 Agent 任务的前置条件同时为“工作区已受信任”和“工作区是 Git 工作区”。非 Git 或未受信任状态只能保留最小只读项目/Git 信息，不能启用任务、运行时启动、项目配置或交接。
- 任务说明为必填文本；可选上下文只能来自用户明确选择的文件、已有 Diff 或补充说明，并在发送前预览。系统不得自动附带完整仓库、全部 Git 历史、配置文件、凭据或完整原始日志。
- 每个任务只有一个由用户选定的主 Agent。Halo 不实现自动分配、并行竞速、自动重试、自动故障转移或隐式代理切换；再次运行和交接均由用户显式触发。
- 任务基线使用只读 Git 检查记录仓库身份、HEAD/无 HEAD 状态、暂存与工作树状态、未跟踪文件清单和受限的比较元数据。脏工作树被允许；无法在容量或脱敏约束下可靠比较的路径必须展示为受限、截断或不可用，而不是归为任务新增修改。
- Halo 可以通过固定的只读 Git 读取器获取状态、Diff 和工作区身份，但不得执行 commit、branch/worktree 创建或切换、stash、reset、merge、push、PR、部署或其他 Git 写操作。Agent 的原生直接写入不经 Halo 代理。
- 任务运行使用既有 Pi/OpenCode 受管运行时和会话适配边界。运行时轨迹、工具状态和真正支持的原生操作请求是瞬时 UI 投影，不默认持久化为完整对话或原始日志。
- 任务状态与交付证据版本分离：一次运行、手动再次运行或交接后的继续工作追加一个版本；仅最新的可审阅交付可得到接受或拒绝结论。取消与失败都保留已有事实和可恢复原因，不自动改写工作区。
- 验证结果只能来源于受管应用原生报告，或由用户显式标为“未执行”。Halo 不提供任意 Shell、测试命令执行或隐式验证能力。
- 交付证据最少包含任务/版本关联、受限摘要、基于任务基线的变更证据、验证结果、生成时间和证据可用性。持久化的 Diff 必须脱敏且有上限；完整原始 Diff 只在当前 Git 状态与任务基线仍支持比较时按需读取，否则给出具体不可用原因。
- 接受与拒绝都只是本地交付结论。接受不得触发 Git 写入、发布或部署；拒绝不得回滚、删除文件、删除任务或抹去历史。
- 交接只允许在当前主 Agent 已结算、已生成证据之后进行。用户必须先预览并确认有界交接包；默认包仅含任务目标、摘要、用户选定变更和验证结果，不含完整对话、原始日志、凭据或配置文件。接收方成为同一任务下一证据版本的主 Agent。
- “审阅请求”是交接目的标签，而不是 Halo 可技术保证的只读模式。接收 Agent 产生任何修改时必须生成新的交付证据版本。
- 交付历史使用本地持久化存储，新增任务、基线、交付证据版本、交接包、结论和配额使用量等专属记录；不保存完整对话或原始工具日志。其模式变更必须通过现有迁移机制演进。
- 配额是可见、用户控制且可预览的本地资源策略。创建需要持久化证据的新任务前应预留最小空间；空间不足时阻止隐式丢失，并要求用户显式增加配额或选择清理范围。清理永远不能静默发生。
- 新 API 以一个固定的“任务与交付”业务域跨 Contracts、Preload、Main、存储与 Renderer 垂直实现。最高测试接缝是 Main 侧任务/交付服务：测试经固定 IPC 输入驱动真实工作区信任、只读 Git 基线、受管运行时适配、持久化证据及公开状态，而非从 Renderer 或私有存储实现开始断言。
- 可借鉴 BitFun 的窄服务接口、运行时与产品特性分离、真实能力状态和渐进垂直切片；不得复制其源代码、资源、品牌、远程/多端/办公/Mini App/开放插件范围。任何未来实质性复用须单独审计 MIT 许可与第三方声明。

## Testing Decisions

- 测试只验证开发者可观察的任务、证据、审阅、交接、配额与安全边界，不为私有表结构、内部缓存或 UI 组件层级编写脆弱断言。
- 最高集成接缝是 Main 侧的固定任务与交付服务。受控 Pi/OpenCode 运行时夹具从工作区信任、Git 工作区判定、任务创建、运行/停止、证据生成到持久化历史验证完整纵向行为。
- Git 基线测试覆盖干净仓库、已有暂存/未暂存修改、未跟踪文件、无初始提交、路径含空格/CJK、任务后新增/修改/删除、比较不可用及工作区身份变化；任何不可靠情况必须是显式状态而非错误归因。
- 安全测试覆盖未受信任或非 Git 工作区不得创建任务、启动任务运行时、读取项目配置或交接；Renderer/Preload 不得暴露任意 Git、文件、Shell、凭据或数据库入口。
- 运行时测试覆盖用户显式选定的单一 Agent、不可用状态、取消、失败、无自动重试/故障转移、原生操作请求透传和运行时轨迹不默认持久化。
- 交付证据测试覆盖追加版本、只有最新可审阅版本可结论、接受不写 Git、拒绝不回滚、取消/失败保留部分事实、验证结果的通过/失败/未执行三态，以及 Diff 脱敏、大小限制、按需读取与不可用说明。
- 交接测试覆盖仅在结算后可发起、预览确认、包内容白名单、默认排除敏感/原始内容、保留同一任务身份、接收方替换主 Agent和审阅请求产生修改时追加新证据版本。
- 存储测试覆盖本地历史重启后恢复、配额使用统计、预留失败、显式清理预览与执行、没有静默删除，以及迁移失败时的安全降级。
- Renderer 测试只通过模拟的固定 Preload API 验证任务工作台的禁用态、错误态、审阅/交接确认、证据可用性提示和文本可访问性；不以 Mock 成功替代 Main/Git/运行时集成测试。
- 每个实施切片至少运行相关单元与集成测试、类型检查和 `git diff --check`；整合阶段运行仓库检查、全量测试、构建及现有 Windows 烟测，真实桌面 GUI 验收仍在有交互式 Windows 宿主的环境执行。

## Out of Scope

- 第三个受管 Agent、通用 Agent 注册、自动委派、Agent 竞速、自动重试、自动故障转移或后台编排。
- 任意 Shell、测试命令执行、终端/PTY、文件写入代理、任意 Git 命令、自动 commit/branch/worktree/PR/推送/部署/回滚。
- 完整对话存档、原始工具日志档案、云同步、团队协作、远程执行、跨设备恢复或云端审计。
- 完整 Monaco 编辑器、文件树重做、通用聊天、完整 TUI、MCP、插件市场、Mini App、办公工作流和多端产品线。
- Pi/OpenCode 凭据、项目配置、完整 Git 历史、完整工作区内容或未获用户选择的上下文自动传入 Agent 或交接包。
- 从 BitFun 复制代码、资源、视觉素材、品牌或其广泛产品范围；参考目录始终只读，不能成为构建、测试、暂存或发布输入。
- 重构整个既有核心、替换 Electron/TypeScript 技术栈，或为本功能引入 Rust/Python sidecar。

## Further Notes

- 本规格承接 ADR 0001 的 Pi/OpenCode 受管边界和 ADR 0002 的可验证交付边界；前者的工作区信任、Main-only 运行时和凭据隔离仍是前置条件，后者的任务与证据术语是本阶段的权威语义。
- `develop` 是唯一开发基线。`main` 的历史实现不可用于回退或重新定向本阶段工作；当前工作树中的用户修改必须保留，并在实施前通过聚焦修正与冗余文件审计恢复一致性。
- 开发工作先以小型纵向切片完成可演示的任务闭环，再推进交接、历史与配额；代码修正和冗余文件剪枝应以消除已发现的重复、死入口、过期文档或不一致契约为准，不做无关重构。
