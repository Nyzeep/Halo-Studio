# Halo Studio Pi 与 OpenCode 受管工作台产品需求

**状态：** 已确认

**日期：** 2026-07-24

**适用范围：** 当前核心重构的剩余交付，以及后续工作台阶段的稳定边界

## Problem Statement

使用 Pi 与 OpenCode 的开发者目前需要分别面对安装、版本、配置、凭据、项目路径和运行状态；旧 Halo Studio 文档又混合了四 Agent、MCP、通用 PTY、Rust/Python sidecar 与 Electron 路线，无法形成可安全实施的单一产品方向。开发者需要一个本地桌面工作台，在不暴露凭据、不绕过项目可信边界的前提下，统一理解和管理 Pi 与 OpenCode。

## Solution

Halo Studio 是一个 Windows 首发、架构兼容 macOS/Linux 的桌面受管工作台。它只支持 Pi 与 OpenCode，并由 Electron Main 进程独占工作区、信任、受管运行时、配置事务、凭据和本地数据。

首个可发布版本（R1）交付安全基础和真实状态：Pi 探测/受管启动边界、OpenCode 受管 Sidecar、工作区信任、配置事务基础、VS Code 风格壳、真实 IPC 状态、受控进程集成测试、Windows 烟测、可复现构建与发布检查。R1 不是完整 IDE。

后续工作台阶段再依次引入结构化会话、精简 Monaco 编辑器、Diff、动态命令目录和受管 TUI 会话；完整配置中心、OpenCode MCP、Pi 资源、同步和跨平台发布继续单独分期。

## User Stories

### R1：受管基础与真实运行时

1. 作为使用 AI 编程工具的开发者，我希望 Halo Studio 只显示 Pi 与 OpenCode，以免旧的 Codex、Claude Code 或其他 Agent 造成误导。
2. 作为开发者，我希望能从桌面界面打开一个本地工作区，以便所有功能共享同一项目上下文。
3. 作为开发者，我希望应用明确显示工作区是否可信，以便决定是否允许读取项目级 Agent 配置和资源。
4. 作为开发者，我希望未信任工作区不会启动项目相关运行时，以免打开陌生仓库就执行其配置。
5. 作为开发者，我希望能看到 Pi 是否已安装、版本是否兼容及其真实生命周期状态，以便先排除本机环境问题。
6. 作为开发者，我希望 Pi 启动时使用明确的工作区、会话、模型和 thinking 配置，而不依赖交互式默认值。
7. 作为开发者，我希望 Pi 在显示可用前完成 `get_state` readiness，以免界面把尚未就绪的进程显示为可用。
8. 作为开发者，我希望 Pi 启动、停止和崩溃状态可重试且不遗留孤儿进程，以便可靠地切换工作区或关闭应用。
9. 作为开发者，我希望 OpenCode 由应用管理的锁定版本 Server 启动，而不依赖 PATH 中任意版本的可执行文件。
10. 作为开发者，我希望 OpenCode 只绑定 loopback 并使用每次启动的新认证信息，以免本机其他进程意外连接。
11. 作为开发者，我希望 OpenCode 在健康检查和精确版本握手完成后才显示运行正常，以便准确判断故障来源。
12. 作为开发者，我希望运行时状态来自 Main 进程 IPC，而不是静态“在线”提示，以便 UI 始终反映真实状态。
13. 作为开发者，我希望工作区切换会停止并清理旧工作区的运行时，以免重新加载界面后恢复过期状态。
14. 作为开发者，我希望模型、thinking 与 Provider 凭据只由 Main 进程解析，以免 Renderer、IPC 或日志接触敏感数据。
15. 作为开发者，我希望凭据仅存于操作系统保护的保险库，并在保护能力不可用时失败关闭，以免产生明文回退。
16. 作为开发者，我希望进程环境采用显式白名单，以免宿主环境中的随机变量或密钥被无意传入运行时。
17. 作为开发者，我希望任何配置写入先展示真实 Diff、要求确认、检测冲突并支持可验证回滚，以免破坏原生配置文件。
18. 作为开发者，我希望 SQLite、日志、Diff、备份和 IPC 都不会泄露明文凭据，以便可以安全诊断问题。
19. 作为开发者，我希望在包含空格和 CJK 字符的 Windows 路径中正常打开工作区并启动运行时，以免路径编码成为发布阻碍。
20. 作为开发者，我希望应用提供 VS Code 风格的标题栏、活动栏、侧栏、中心区、Agent 辅助栏、底部面板和状态栏，以便快速理解当前项目与运行时状态。
21. 作为开发者，我希望小屏幕下工作台区域不会重叠、长路径不会溢出，以便在不同窗口尺寸下稳定使用。
22. 作为维护者，我希望通过一个开发命令同时准备依赖并启动 Electron 与 Vite，以便开发时验证真实桌面边界而非仅浏览器页面。
23. 作为维护者，我希望仓库检查拒绝参考目录、旧 Agent、Mock PTY、旧 Web fallback 和硬编码本机路径进入运行时代码，以便持续保持重构边界。
24. 作为维护者，我希望验证链覆盖类型检查、单元测试、集成测试、构建、依赖审计和 Windows 烟测，以便每次发布都有可复现证据。

### 后续工作台阶段：已定义边界，非 R1 验收项

25. 作为开发者，我希望在 GUI 中以结构化界面查看和发送 Pi 会话消息，以便不必把终端作为主要交互。
26. 作为开发者，我希望在 GUI 中以结构化界面查看和发送 OpenCode 会话消息、工具事件和权限请求，以便区分原生状态而不伪造统一能力。
27. 作为开发者，我希望输入 `/` 后只看到当前受管应用真实支持的命令，以便避免跨应用误发或把 TUI 专属命令伪装为 GUI 能力。
28. 作为开发者，我希望可以显式打开当前工作区的受管 TUI 会话，以便在 GUI 内继续使用 Pi 或 OpenCode 的原生命令语义。
29. 作为开发者，我希望受管 TUI 会话不携带 Halo 保存的凭据，也不成为任意 Shell 入口，以便调试能力不破坏安全边界。
30. 作为开发者，我希望获得精简的 Monaco 编辑器、文件树、脏文件、查找替换、保存和 Diff，以便完成日常项目查看与受管修改审阅。
31. 作为开发者，我希望从 Agent 变更定位到 Diff 和编辑器位置，以便理解修改而不是盲目接受。
32. 作为开发者，我希望管理 Pi 的 Skills、Prompts、Extensions 和 Packages，以及 OpenCode 的真实配置能力，以便统一配置体验但不混淆两者协议。
33. 作为开发者，我希望管理 Provider、Profile、凭据引用和代理策略，以便在不暴露密钥的情况下切换受管启动配置。
34. 作为开发者，我希望 OpenCode MCP 仅在其原生能力和安全写入流程准备就绪后出现，以便不把 Pi MCP 或伪 MCP 当作产品能力。
35. 作为跨平台开发者，我希望 macOS 与 Linux 使用相同的进程、凭据和 IPC 边界，以便后续发布不会推翻 Windows 首发架构。
36. 作为维护者，我希望后续同步、更新、托盘和国际化在本地安全模型稳定后再加入，以便不提前扩大攻击面和数据责任。

## Implementation Decisions

- 产品边界固定为 Pi 与 OpenCode 两个受管应用；不保留通用 Agent 注册表，也不维护 Codex、Claude Code 或其兼容层。
- Renderer 只承载 UI 与瞬时视图状态；Preload 只暴露按业务域划分、经 Schema 校验的固定 API；Main 独占文件、进程、数据库和凭据。
- 一个活动工作区是应用中项目路径与信任状态的唯一事实来源。工作区切换、信任改变和关闭都必须收敛对应运行时。
- Pi 使用 JSONL RPC 与 `get_state` readiness；OpenCode 使用精确锁定的本地 Server、loopback、随机 Basic Auth、健康检查和版本握手。
- Pi 的模型、thinking、Provider 凭据和会话启动参数必须由 Main-only 的受管启动配置解析，不经 Renderer 或 IPC 输入，也不硬编码为产品默认值。
- OpenCode 本地认证和任何 Provider 明文凭据都不属于公开运行时快照、日志、Diff、备份或数据库事实数据。
- 配置文件仍是原生事实来源；Halo 只保存自身元数据、凭据引用、审计和备份元数据。配置变更使用预览、确认、指纹冲突检测、原子替换和回滚。
- UI 使用紧凑、安静、VS Code 风格的信息架构，但 R1 不安装 Monaco，也不创建假的编辑器、会话、终端或命令执行 API。
- 后续终端只能作为受管 TUI 会话：用户显式开启、绑定受信任工作区、仅面向 Pi/OpenCode，并与 Agent RPC transport 隔离。任意 Shell/PTY 需要独立安全规格，当前不授权。
- R1 以 Windows 为验收平台，同时保持路径、进程、凭据和打包边界可移植；macOS/Linux 发布不作为 R1 阻塞条件。
- `develop` 是活跃重构分支；提交信息使用中文且单一职责。参考代码目录永远只读、不可构建、不可暂存或提交。
- 本文档是需求层面的唯一活动来源；历史四 Agent、原生 Rust/Python、MCP/通用 PTY 计划只保留为追溯材料，不能直接生成实现任务。

## Testing Decisions

- 测试以用户可观察行为和安全边界为目标，不断言私有实现细节或将测试夹具变为生产回退路径。
- 运行时的最高集成接缝是 Main 侧桌面服务组合：它接收固定 IPC 输入、拥有工作区信任、创建运行时并返回公开状态。受控 fake Pi/OpenCode 进程从这一接缝验证真实生命周期。
- Pi 集成测试验证版本探测、JSONL 分帧、乱序响应、`get_state` readiness、EOF、无效 JSON、`agent_end` 重试语义、停止和凭据边界。
- OpenCode 集成测试验证 loopback 绑定、Basic Auth、健康 401/500/200、版本不匹配、SSE 心跳、退出和优雅停止。
- 工作区测试验证真实路径、替换目录、信任撤销、单活动工作区、空格/CJK 路径和运行时清理。
- 凭据边界测试使用唯一 canary，断言其仅可在保险库密文中存在，且不出现在 SQLite、IPC、日志、Diff、审计、备份或 UI 状态中。
- Renderer 测试只经模拟的固定 Preload API 验证 UI 状态、可访问性、响应式布局与错误恢复；不让 Renderer 直接访问 Node、Shell 或 loopback 服务。
- 验收运行完整仓库检查、类型检查、测试、构建、依赖审计、Windows 路径烟测和开发态 Electron 烟测。

## Out of Scope

- Codex、Claude Code、Gemini、Hermes、OpenClaw 或任何第三个受管应用。
- 旧多 Agent 注册表、旧 Web fallback、静态假运行时、Mock PTY、宇宙主题和旧数据迁移。
- R1 中的完整 Monaco 编辑器、文件修改、完整聊天、工具权限流、会话恢复、`/` 命令执行、TUI 会话或嵌入式终端。
- 任意 Shell、任意命令执行、任意路径读写、通用 SQL 查询和通用 IPC invoke。
- Pi MCP、伪 MCP、OpenCode MCP 的提前交付。
- 云同步、托盘、自动更新、国际化、macOS/Linux 发布和完整 IDE 生态。
- 修改、构建、安装依赖或提交只读参考代码目录。

## Further Notes

- 当前剩余 R1 工作应先完成受控 Pi/OpenCode 集成测试、Windows 烟测、活动文档、仓库卫生、完整验证和 `develop` 推送；随后再开启下一个垂直切片。
- 发布规格和任务时使用 GitHub Issues；任务采用 `ready-for-agent` 标签并显式记录阻塞关系。
