# 02 - 受管事件事实与交付证据投影规格

## 问题陈述

本地开发者需要在 Halo Studio 重启后重新查看受管任务的可靠状态和已冻结的交付审查，而当前 Runtime 只有瞬时运行轨迹和独立的中断记录。若直接保存或暴露 Pi/DSH 原始 session、JSONL、消息或工具输出，会同时破坏 Halo Workbench Runtime 的单一权威、隐私边界和 P0 Adapter 边界；若把事件日志当成交付证据，又会绕过任务基线、工作区指纹、证据新鲜度和人工审查。

## 解决方案

在 Halo Workbench Runtime 内建立一个深的事件事实 Module。它通过小型、typed Interface 接收 Runtime 已规范化的受管任务事实，统一完成版本化、顺序、幂等、脱敏、大小限制、恢复和本地保留策略；内存 Adapter 是首个可验证实现，持久化 Adapter 在后续切片接入。Runtime 从此事实序列投影受管任务快照和运行轨迹，并以事实、任务基线和工作区指纹独立生成可冻结的交付证据快照。

Pi/DSH 只处于入站 Adapter 外侧。它们的原始事件、session、模型内容、工具参数、工具输出、凭据和 JSONL 永远不成为 Halo 事实或 UI Interface。重启不会自动恢复执行、重放操作、重新运行工具或自动接受交付。

## 用户故事

1. 作为本地开发者，我希望每个受管任务都有经脱敏和限长处理的事实历史，以便在不暴露敏感执行内容的情况下理解其过程。
2. 作为本地开发者，我希望关闭并重新打开应用后仍能看到当前受管任务的状态快照，以便决定下一步处置。
3. 作为本地开发者，我希望未结束任务在重启或状态不一致后明确显示为 `interrupted`，以便不会误以为它仍在运行或已完成。
4. 作为本地开发者，我希望重新打开交付审查页时看到冻结的证据快照、覆盖范围和新鲜度，以便重新审查而不重跑任务。
5. 作为本地开发者，我希望覆盖文件被后续修改时证据自动标记为 `stale`，以便不能接受已经失真的交付。
6. 作为本地开发者，我希望只有我能显式接受或拒绝交付，以便事实恢复和事件回放不会替代人工决议。
7. 作为本地开发者，我希望高风险 Agent 操作请求和一次性决议有可审查摘要，以便知道任务为何暂停或继续。
8. 作为本地开发者，我希望任务基线、文件变更指纹和证据版本能够关联，以便审查范围可追溯。
9. 作为本地开发者，我希望重复到达的同一事实输入具有确定结果，以便协议重试不会把历史或证据夸大。
10. 作为本地开发者，我希望旧版本的已保存事实仍然可读，以便本地历史不会因 schema 追加演进而丢失。
11. 作为隐私敏感的开发者，我希望完整 prompt/response、密钥、原始工具参数和输出绝不进入事件历史，以便本地留存保持最小暴露面。
12. 作为使用 Pi RPC 的开发者，我希望新增事件事实能力不改变 Pi RPC 的 P0 唯一生产 Adapter 地位，以便执行链不发生隐式替换。
13. 作为未来评估 DSH 的开发者，我希望 Runtime 可以接收经 Adapter 允许的摘要输入，而不把 DSH session schema 变成 Halo 的产品契约。
14. 作为维护者，我希望 UI 只通过 Runtime 的 typed snapshot 和投影读取信息，以便存储实现、外部执行器和敏感原始数据保留在深 Module 内。
15. 作为本地历史的所有者，我希望可以按产品策略删除事实与证据，以便长期保留不等于永久不可删除。

## 实现决策

### 预先确认的 seam

- 外部 Interface 保持为 Halo Workbench Runtime 已有的 typed snapshot、intent 和有序运行时投影；前端不新增事实库查询或执行器日志读取入口。
- 内部 seam 是 Runtime 所有的 `ManagedEventFacts` Interface。首片只表达 append 规范化事实和读取某任务可恢复快照所需事实；本地历史删除在持久化与保留策略切片中以受控 Runtime 操作接入。调用方不需要理解存储格式、索引、脱敏、限长、schema 升级或投影水位。
- 首个 Adapter 是纯内存 fake；生产持久化必须是第二个 Adapter，才证明该 seam 真实存在。它不能借用中断快照替换存储、交付证据 port 或 UI 广播事件作为事件事实日志。

### 事件事实模型

- 每条事实包含 Halo 本地事实身份、受管任务身份、单调任务内顺序、记录时间、schema 版本、闭合事实种类和经允许的摘要字段。事实种类至少覆盖任务生命周期、用户/Agent 摘要、工具活动、高风险操作请求与一次性决议、文件变更指纹、任务基线关联、证据版本和新鲜度变化。
- 同一任务内重复提交相同事实身份必须幂等，不追加第二条事实；不同事实身份即使摘要相同也按到达顺序保留。顺序、重复和失败语义由 Runtime 的事实 Module 集中决定。
- schema 只追加演进。读取方必须识别已支持的旧 schema，并对未知且不可安全解释的事实 fail closed；不得把 DSH 的可忽略事件约定继承为 Halo 的兼容承诺。
- 事实正文在进入存储前统一脱敏和限长。禁止字段包括完整模型 prompt/response、凭据或密钥、原始工具参数、完整工具输出、原始 Pi/DSH JSONL、外部执行器原始 session log，以及能重新建立它们的未脱敏载荷。

### 入站 Adapter 与生命周期

- Pi/DSH 输入先由各自 Adapter 处理，Runtime 只接收允许的 Halo 摘要和状态。外部 source identity 可以只用于入站去重和诊断，不能成为 Renderer 或交付证据的公开标识。
- Runtime 在受管任务生命周期的规范化位置写入事实，并把 append 失败视为受控失败；不得悄悄让 UI 状态推进而事实历史缺口不可见。
- 重启只加载 Halo 本地事实并重建快照。它不恢复 Pi/DSH 会话，不重新发送 prompt，不重放工具或 Agent 操作请求，不自动重新执行任务。若活动事实与工作区或外部执行器不一致，任务变为 `interrupted`；若冻结证据的覆盖范围不一致，证据变为 `stale`。

### 交付证据投影

- 交付证据快照由事件事实、任务基线和工作区指纹独立投影并冻结，不复用事件序列本身作为证据。
- 快照记录证据版本、覆盖文件、覆盖范围、任务基线关联、验证摘要和新鲜度。覆盖文件的后续变化必须产生可投影的失效事实并使相关快照 `stale`。
- 只有本地开发者提交的接受或拒绝 intent 能改变交付结论；回放、重建、外部事件或证据投影本身没有该权限。

### 保留、删除和 UI 投影

- 事件事实与证据遵循同一套 Halo 本地历史保留、统一脱敏和大小上限策略；用户删除时必须同时更新可见快照，不能留下可从投影反推的敏感残留。
- Renderer 只读取 Runtime 的 typed Interface。Runtime 内部存储、Adapter 原始数据、诊断细节和投影实现都不是 UI 合同。

## 测试决策

- 所有测试从确认的 seam 观察行为：对事实 Module 使用内存 Adapter；对 Runtime 使用其公开 snapshot、intent 和投影事件。测试不查询内部锁、直接读取存储文件，也不 mock 自己的 Module。
- 契约测试必须覆盖：事件顺序、相同事实身份的重复输入、旧 schema 读取、脱敏、大小上限、可恢复任务快照、重启后的 `interrupted` 归类、证据新鲜度失效，以及回放不能替代人工接受或拒绝。
- 交付证据测试必须从任务基线、工作区指纹和事实输入生成快照，随后改变覆盖文件以证明 `stale`；它不以事件日志对象本身作为断言目标。
- 前端契约测试只能验证 typed projection 的形状与展示状态，且要证明它不接触原始 Pi/DSH 标识、凭据、原始工具参数/输出或事实存储。
- 先例是现有 Workbench Runtime 的公开契约测试、任务基线与交付证据 port fake，以及 Pi RPC Adapter 的协议契约测试。每一轮采用 red → green 的单个 tracer bullet，不提前实现后续持久化或 UI 功能。

## 不在范围内

- 真实 DSH runtime、`core/session`、Cordis lifecycle 或 DSH persistence 的集成测试和生产集成。
- 真实 Pi/模型会话验收、原始 Pi session 恢复或任何真实 JSONL 重放；这些验收保持 `not-run`，直到单独授权并在验收工作区执行。
- 自动恢复、自动重试、自动重放工具/执行器、自动接受或自动拒绝交付。
- OpenCode/ACP/旧 Sidecar 的恢复、第二生产执行 Adapter、Pi RPC 替换或 TypeScript/Cordis 基座迁移。
- 将事件事实作为通用聊天档案、遥测平台或未受控的外部日志出口。

## 补充说明

- 本规格落实 ADR-0075。DSH 的 append-only 事件、纯投影、版本拒绝和持久化协调模式仅是设计参考；Halo 采用自己的 schema、Adapter 和权威边界。
- 本规格拆分为三个 blocker-first 的 tracer-bullet 任务：事件事实契约与内存 Adapter seam、Runtime 写入/恢复/脱敏/大小上限、证据投影/新鲜度/typed UI projection。每个任务达到完整规格和验收后才使用 `ready-for-agent`。
