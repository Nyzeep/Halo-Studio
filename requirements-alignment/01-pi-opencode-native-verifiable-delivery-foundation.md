# 01 - Pi/OpenCode 原生工作台的可验证编码交付基础

**状态：** 已确认<br>
**对齐日期：** 2026-07-26<br>
**适用范围：** Halo Studio 首个原生 UI 可交付版本及其迁移基础

## 问题陈述

本地开发者同时使用 Pi 与 OpenCode 时，缺少一个能在单一可信 Git 工作区中安全启动运行时、明确任务输入、展示真实执行状态、审查变更并保留交付证据的桌面工作台。现有 Electron 多 Agent 终端外壳与产品方向不一致，既混入了不再支持的 Agent，也无法可靠区分任务、变更、验证和用户决定。

BitFun 提供了可借鉴的运行时分层、能力边界、审查生命周期和扩展治理思路，但其通用 AI 平台、办公、Mini App、远程多端与 WebView 技术路线不适合 Halo Studio 的首期目标。

## 解决方案

Halo Studio 重建为 Windows 首发的原生开发工作台，采用 **PySide6/QML + Rust Runtime Sidecar**。产品只受管 Pi 与 OpenCode，并面向本地开发者提供一个完整、可验证的编码交付闭环：

1. 打开并信任一个 Git 工作区。
2. 显式创建任务，并选择 Pi 或 OpenCode 为主 Agent。
3. 记录任务基线，显示真实运行状态与结构化运行轨迹。
4. 审查任务关联变更、只读 Diff 和验证结果。
5. 接受、拒绝，或在可审查交付结束后手动交接给另一受管应用。

Halo Studio 负责安全边界、任务归因、交付证据和审查；Pi/OpenCode 保留各自原生的运行、写入、权限和交互语义。

## 用户故事

1. 作为本地开发者，我希望 Halo Studio 只显示 Pi 与 OpenCode，避免旧的多 Agent 入口造成误导。
2. 作为本地开发者，我希望显式打开一个 Git 工作区，以便所有任务、运行时和交付证据具有唯一项目上下文。
3. 作为本地开发者，我希望确认工作区是否可信，以便陌生仓库不能自动影响本机运行时。
4. 作为本地开发者，我希望未信任工作区只能查看基本状态，不能加载项目 Agent 配置、插件或启动运行时。
5. 作为本地开发者，我希望一次只激活一个工作区，以便切换项目时旧 Agent 进程被可靠停止和清理。
6. 作为本地开发者，我希望显式创建任务说明并选择 Pi 或 OpenCode，以便明确当前由谁负责交付。
7. 作为本地开发者，我希望任务只携带我选定的说明、文件、已有 Diff 和补充信息，以便控制初始上下文。
8. 作为本地开发者，我希望任务开始时记录 Git 基线，以便区分任务前已有改动和任务后的关联变更。
9. 作为本地开发者，我希望在任务运行期间仍能手动编辑代码，但系统应诚实地标记人工介入，不能把所有后续改动都声称为 Agent 编写。
10. 作为本地开发者，我希望 Pi/OpenCode 使用各自真实协议启动和就绪检查，以便界面只展示可信的可用性状态。
11. 作为本地开发者，我希望任务过程以结构化轨迹呈现，以便了解当前阶段、操作请求和验证状态，而不是阅读原始终端文本。
12. 作为本地开发者，我希望 Pi/OpenCode 仍按原生权限模型直接修改工作区，以便 Halo Studio 不伪造统一权限或写入语义。
13. 作为本地开发者，我希望可以在任务结束后查看只读文件变更和 Diff，以便在不离开审查流程的情况下判断结果。
14. 作为本地开发者，我希望看到验证通过、失败或未执行的真实结论，以便不把未验证的任务误认为已完成。
15. 作为本地开发者，我希望接受交付只记录我的结论，不自动提交、推送、建分支或发布。
16. 作为本地开发者，我希望拒绝交付不会自动删除文件或回滚工作区，以便保留人工修改和后续修复空间。
17. 作为本地开发者，我希望重试或交接产生追加式交付证据版本，以便回看失败、修复和审查过程。
18. 作为本地开发者，我希望在可审查交付结束后手动创建精简交接包，以便另一个 Agent 接续或复查，而不暴露完整对话、原始日志、凭据和配置文件。
19. 作为本地开发者，我希望取消任务先请求 Agent 原生停止，超时才强制终止，并能看到最终取消状态。
20. 作为本地开发者，我希望任务和交付历史只留在本机，且不会保存明文凭据、完整原始对话或无限原始日志。

## 实施决策

- 产品只受管 Pi 与 OpenCode。Claude Code、Codex 与其他 Agent 不进入新产品范围。
- 首期定位为可验证编码交付工作台，不扩展为通用 AI 平台、办公产品或多端协作产品。
- 使用 PySide6/QML 承担原生界面；Rust Runtime Sidecar 独占任务、运行时、配置事务、本地数据与安全敏感能力。
- QML 与 Rust Sidecar 采用版本化 `stdio JSONL` 通信。首期不引入命名管道或二进制协议。
- Rust Sidecar 将不同 Agent 的输出转换为带任务 ID、序号、时间、事件类型和载荷的有序运行时事件，并维护快照与有限事件缓冲以支持界面恢复。
- 首期一个活动工作区中同一时刻只运行一个 Agent 任务；跨 Agent 协作只能通过任务结束后的用户审查与手动交接完成。
- Pi 以 RPC 模式和 `get_state` 就绪检查受管启动；OpenCode 使用锁定版本的回环本地服务、每次启动的新认证信息、健康检查和精确版本握手。
- Pi/OpenCode 的模型、思考级别、Provider 凭据引用和启动选项通过受管启动配置管理。凭据只由安全后台短暂读取，不暴露给 UI、IPC、日志、Diff、备份或数据库。
- 工作区必须是经真实路径校验并由用户确认的 Git 工作区。打开新工作区、撤销信任或退出应用时，旧运行时必须停止和清理。
- Agent 原生写入工作区；Halo Studio 不代为应用补丁、自动暂存或自动回滚。任务基线后的变更称为任务关联变更；发生人工编辑时不得声称全部由 Agent 编写。
- 交付审查提供只读变更与 Diff，不提供完整编辑器、文件写入、查找替换或保存能力。
- 验证结果仅来自受管应用原生运行时，或由用户明确标记为未执行。Halo Studio 不自行执行任意测试或命令。
- 接受和拒绝只记录任务结论。它们不得自动提交 Git、推送远端、创建分支、发布、删除任务或回滚工作区文件。
- 重试和交接创建追加式交付证据版本，旧结果不可被覆盖。自动委派、自动重试和自动故障转移不在范围内。
- 交接只能发生在可审查交付结束后，由用户预览并确认精简交接包。默认排除完整对话、原始工具日志、凭据和配置文件。
- 首期不自动恢复或重放中断的 Agent 执行。应用重启或运行时崩溃后，任务必须如实标记，由用户决定重试或交接。
- 主界面以活动工作区、任务状态、结构化运行轨迹、交付证据和文件变更为中心。终端只作为后续受管 TUI/诊断能力，不是主交互。
- 未来受管 TUI 仅在受信任工作区中、由用户显式打开并且只面向 Pi/OpenCode；它不是任意 Shell，也不携带 Halo Studio 保存的凭据。
- 配置写入与 Agent 任务分离，必须经过真实 Diff、用户确认、冲突检测、原子写入和可验证回滚。
- 首期配置界面只覆盖安全启动任务所需的最小能力。MCP、插件、Skills、Prompts、扩展市场、自动发现和完整原生配置资产管理延期，且未来必须按 Pi/OpenCode 原生语义分别设计。
- Windows 是首发与验收平台；路径、进程、凭据和 IPC 边界保持可移植，但 macOS/Linux 不阻塞首期发布。
- 原生 UI 采用干净重建策略：旧 Electron 代码仅作为只读参考，不保留兼容运行入口、旧 Mock 数据或旧数据迁移。
- 数据仅在本机保存。首期不做云同步、账户体系、远程协作或跨设备恢复。

## 测试决策

- 主要测试接缝是版本化的“QML/应用控制层 -> Rust Sidecar IPC 契约”。界面测试使用符合该契约的测试 Sidecar；集成测试使用真实 Sidecar 与受控 Pi/OpenCode 进程。
- 测试替身仅用于测试。生产环境不得回退到模拟 Agent、假在线状态或假任务结果。
- 每个迁移阶段的完成证据包括：Rust 单元与契约测试、QML/ViewModel 行为测试、受控进程集成测试、Windows 原生应用烟测以及工作区/凭据边界检查。
- 好的测试验证用户可观察的行为和安全边界，不断言私有实现细节。
- 集成测试应覆盖：工作区信任和切换、Pi/OpenCode 就绪失败、事件乱序或丢失恢复、取消超时、任务基线、人工介入提示、交付接受/拒绝、手动交接以及凭据不可见性。

## 范围外

- 第三个受管 Agent、旧多 Agent 注册表和任何兼容层。
- 通用 AI 办公、Mini App、远程执行、云同步、多端协作、账户体系和扩展市场。
- 自动委派、自动重试、自动 Agent 故障转移、自动 Git 操作和自动发布。
- 完整编辑器、文件修改、嵌入式通用终端、完整聊天会话、自动会话重放和任意命令执行。
- 首期 MCP、插件、Skills、Prompts、自动发现和完整 Pi/OpenCode 配置资产管理。
- macOS/Linux 发布与完整跨平台验收。

## BitFun 借鉴边界

借鉴：运行时与界面分层、能力/适配器边界、审查生命周期、扩展权限治理、故障状态透明化。

不借鉴：Tauri/WebView 界面承载、通用 AI 平台定位、办公与 Mini App 能力、远程多端与广泛生态兼容范围。
